# Zagros v1.0.0-alpha.8.8

## Release summary

Alpha 8.8 unifies the two user-level resource contracts across every active
Core:

1. one persistent traffic/accounting total per User; and
2. one aggregate download bucket plus one aggregate upload bucket per User.

The bandwidth limiter is kernel datapath enforcement, not dashboard accounting.
Xray, sing-box, OpenVPN, WireGuard, SoftEther native, SSTP, L2TP/IPsec, raw
L2TP, PPTP/ACCEL-PPP and SSH forwarding all resolve their stable identity into
the same User actions.

This remains an alpha release. Back up the database and `/var/lib/zagros`
before upgrading.

## Per-user traffic accounting

- Core counters fold into one platform User, legacy total, quota row and usage
  journal identity.
- Reconnects, process generations and provider counter resets never subtract or
  double count usage.
- Persistent baselines make restarts exactly-once.
- Xray provider aliases and every non-Xray account map to the same owner.
- Shutdown drains live counters before managed Core processes stop.
- One User's traffic cannot be charged to another User.

## Aggregate bandwidth limits

Users have two strict non-negative integer fields in Mbps:

```text
download_limit_mbps
upload_limit_mbps
```

`0` means Unlimited. Existing users upgrade to `0/0` and remain unshaped.
Upload and download are independent.

Each non-zero direction owns one standalone global `tc police` action. Every
Core, connection, process and IP family binds that same action index. Adding a
second protocol therefore shares tokens; it does not multiply the configured
rate.

Stable datapath identities include:

- Xray and sing-box: canonical per-user socket/routing marks;
- OpenVPN, WireGuard and PPTP: deterministic inner addresses;
- SSH: Unix UID;
- SoftEther native/SSTP/L2TP: authenticated outer session plus routed-TAP DHCP
  identity.

Unknown SoftEther transports enter a conservative fail-closed quarantine until
authenticated identity is known.

## Xray/Shadowsocks bypass closure

The release validation reproduced the reported issue. Xray sockets carried the
correct mark, but candidate8 installed only `protocol ip` tc classifiers while
the host and Xray freedom outbound used global IPv6. A dual-stack speed test
could therefore bypass shaping.

Alpha 8.8 adds IPv6 conntrack, ingress and egress filters that bind the exact
same actions as IPv4. On the same User and endpoint with a 5 Mbps limit:

```text
before: 208.194 Mbps
 after:   4.758 Mbps
```

TCP and UDP upload/download passed over both IPv4 and IPv6. A second fix keeps
legacy Xray emails compatible while resolving kernel marks to the canonical
platform User ID; intentionally divergent legacy/platform IDs were validated
on the real datapath.

## OpenVPN and SoftEther listener safety

A stale SoftEther OpenVPN-compatibility switch could persist in
`vpn_server.config` even while panel settings said it was disabled. When the
real OpenVPN Core released UDP/1194 for restart, the clone claimed the port and
blocked restart with `EADDRINUSE`.

The SoftEther driver now reasserts the disabled runtime state idempotently.
Two consecutive real OpenVPN restarts passed, and the only final UDP/1194 owner
was the real OpenVPN process.

## Migration

Alembic revision:

```text
0011_user_bandwidth_limits
```

It adds data-preserving, non-null zero-default columns to both platform and
legacy user schemas. It does not reset usage, journal entries, baselines,
credentials, grants or Core state.

The chain was validated from alpha.8.7-era schema/data to head and on copies of
the deployed SQLite databases. Downgrade metadata removes only the two added
columns according to the repository's current Alembic contract; always restore
a backup for operational rollback.

## Verification

- full source suite: **970 passed, 8 skipped, 0 failed**;
- Xray TCP/UDP IPv4/IPv6 at 5 Mbps: **4.65–4.93 Mbps** receiver rates;
- Xray download at 100 Mbps with 1/2/4/8 connections:
  **98.729 / 97.924 / 96.371 / 95.992 Mbps** aggregate;
- Xray upload at 50 Mbps with 1/2/4/8 connections:
  **44.805–46.844 Mbps** aggregate;
- seven active Cores, complete simultaneous uploads at a 50 Mbps User limit:
  **46.185 Mbps** aggregate;
- cross-user concurrent validation: Unlimited offered 20.021 Mbps, a 10 Mbps
  User measured 9.723 Mbps, and a 100 Mbps User measured 99.408 Mbps;
- dynamic active-session update passed 50 → 20 → Unlimited → 20 → 100 Mbps;
- reconnect, Xray/OpenVPN Core restart, limiter reconcile and container
  recreation retained identity and limits;
- raw L2TP, L2TP/IPsec and SSTP real clients passed bidirectional traffic;
- dashboard bundle and API expose both fields and `0 = Unlimited`.

The validation hosts each exposed only one vCPU. No fake multi-CPU result is
claimed. The limiter contains no per-CPU bucket/map: all classifiers reference
one global kernel action object, and multi-process/multi-namespace tests
consumed that shared state.
